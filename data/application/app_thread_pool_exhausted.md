# 应用线程池耗尽 / 请求堆积诊断与处理

## 问题现象

请求响应变慢、大量请求排队；线程池抛 `RejectedExecutionException`；接口超时增多、吞吐下降。

**与"CPU 飙高""慢查询"的区别**：CPU 不一定高——线程多半是**阻塞在等下游**（DB、外部接口），而非在算。属于"响应慢"家族，需用堆栈区分根因。

## 排查步骤

### 1. 打线程堆栈，看线程都卡在哪

```bash
jstack <PID> > /tmp/jstack.log
grep -c "java.lang.Thread.State: BLOCKED" /tmp/jstack.log    # 阻塞线程数
grep -c "WAITING (on object monitor)" /tmp/jstack.log
# 多次采样对比，看大量线程是否都停在同一个下游调用（DB / HTTP 客户端）
```

### 2. 看线程池与下游耗时

- 业务线程池活跃数 / 队列长度是否持续打满。
- 下游 DB（慢查询）、外部接口（RT 飙升）是否在拖慢线程释放。

## 常见原因

- **下游变慢**：DB 慢查询 / 外部接口超时，线程长时间占用不释放——最常见。
- **线程池过小**，扛不住并发。
- **没设超时**：调用下游无超时，一个慢依赖拖垮整个池。
- 任务里有锁竞争 / 死锁，线程阻塞。

## 解决方案

### 临时止血

- 临时调大线程池 / 队列，或对非核心功能降级、限流。
- 重启释放堆积线程，先恢复可用性。

### 根本修复

- **给所有下游调用设超时 + 熔断**（一个慢依赖不能拖垮全局）。
- 优化下游：DB 慢查询加索引、外部接口加缓存 / 异步化。
- 按"小核心池 + 有界队列 + 合理拒绝策略"配置线程池，避免无界堆积。
- IO 密集场景考虑异步 / 响应式，减少线程阻塞占用。

## 预防措施

- 监控线程池活跃线程数、队列长度、拒绝次数。
- 所有跨进程调用**强制设置超时**，纳入代码评审红线。
- 压测验证下游变慢时系统是否优雅降级而非雪崩。
