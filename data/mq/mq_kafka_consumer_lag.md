# Kafka 消费积压（Consumer Lag）诊断与处理

## 问题现象

消费者 lag 持续增长、迟迟消费不完；下游数据延迟（订单状态、通知、报表滞后）；消费速度跟不上生产速度，消息堆积在 topic 里。

## 排查步骤

### 1. 看消费组 lag

```bash
kafka-consumer-groups.sh --bootstrap-server <broker> \
  --describe --group <消费组>      # 看每个分区的 LAG（堆积量）、CURRENT-OFFSET、LOG-END-OFFSET
```

### 2. 判断瓶颈在哪

- 各分区 lag 是否均匀（不均 → key 倾斜 / 分区分配不均）。
- 单条消息**消费耗时**：消费逻辑里是否调了慢 DB / 慢接口。
- 是否**频繁 rebalance**（消费者频繁加入退出 → 消费停顿）。
- 消费者实例数是否 < 分区数（并行度受限）。

## 常见原因

- **消费速度 < 生产速度**：突发流量或消费逻辑慢。
- **消费逻辑里有慢操作**（同步写 DB、调外部接口），单条处理慢。
- **分区数不足**，限制了消费并行度（消费者数 ≤ 分区数）。
- 频繁 rebalance（`max.poll.interval.ms` 内没处理完导致被踢）。
- 消费异常 + 无脑重试，卡在某条"毒消息"上。

## 解决方案

### 临时止血

- **增加消费者实例**（但不超过分区数，否则多余实例空闲）。
- 临时对积压做**批量 / 并行**处理，或先跳过非关键消息。

### 根本修复

- **优化消费逻辑**：批量写库、异步化、去掉同步慢调用。
- **增加分区数**提升并行上限（注意 key 顺序性影响）。
- 调 `max.poll.records` / `max.poll.interval.ms`，避免处理超时被踢。
- 消费**幂等 + 死信队列**：毒消息进 DLQ，不阻塞主流程。

## 预防措施

- 监控 consumer lag，持续增长即告警。
- 分区数按峰值吞吐预留并行度。
- 消费幂等设计，配置合理重试与死信队列。
