# 数据库死锁（Deadlock）诊断与处理

## 问题现象

事务报 `Deadlock found when trying to get lock; try restarting transaction`；部分事务被自动回滚、业务偶发失败；高并发下出现请求卡住后超时。

**与"慢查询"的区别**：死锁是多个事务**互相等对方持有的锁**，不是单纯执行慢——加索引提速救不了死锁。

## 排查步骤

### 1. 看最近一次死锁详情（MySQL/InnoDB）

```sql
SHOW ENGINE INNODB STATUS\G   -- 看 LATEST DETECTED DEADLOCK 段，含两个事务的 SQL 与持锁/等锁
```

### 2. 看当前锁等待与阻塞关系

```sql
SELECT * FROM performance_schema.data_lock_waits;     -- 谁在等谁
SHOW PROCESSLIST;                                      -- 长事务 / 卡住的连接
SELECT * FROM information_schema.INNODB_TRX;           -- 运行中的事务及其耗时
```

## 常见原因

- **多个事务加锁顺序不一致**（A 先锁表1再锁表2，B 反过来）——最典型。
- **长事务**：事务里夹了远程调用 / 慢逻辑，长时间持锁。
- **缺索引导致锁范围过大**：行锁退化为间隙锁 / 锁住大量行，冲突概率飙升。
- 一次更新过多行的大事务。

## 解决方案

### 临时止血

```sql
KILL <被阻塞或长事务的连接ID>;   -- 解开当前僵持
```

### 根本修复

- **统一加锁顺序**：所有事务按相同顺序访问多张表 / 多行。
- **缩短事务**：事务内只放必要的 DB 操作，移除远程调用与慢逻辑。
- **加索引缩小锁范围**：让 WHERE 命中精确行锁，避免大范围加锁。
- 业务层加**死锁重试**（捕获死锁错误码后重试），并降低隔离级别（如 RR → RC）减少间隙锁。

## 预防措施

- 监控死锁次数与锁等待时长，设告警。
- 代码评审重点看事务边界、加锁顺序、事务内是否有 IO / RPC。
- 高并发表的更新走索引、保持事务短小。
